# Поступашки: куда исчезает маркетинг?
 
Система измерения эффективности рекламы через Telegram-бота: откуда приходят
покупатели и какие каналы реально приносят деньги.
Решение кейса хакатона «Аналитика вне SQL».

## Контекст и постановка задачи
 
Поступашки - школа подготовки к поступлению, стажировкам и работе в
IT. Весь маркетинг и продажи идут через Telegram: контент, скидки,
нативные интеграции, реклама в сторонних каналах, а после переписки с
менеджером покупатель получает доступ к курсу.
 
Проблема в том, что бизнес фиксирует только сам факт оплаты. Всё, что
происходит до неё - какая реклама сработала, откуда пришёл человек, сколько
касаний было исторически нигде не логировалось. Воронка выглядит как
чёрный ящик:
 
```
Реклама → Переход/просмотр → Основной канал → Менеджер → Оплата → Курс
 (не видно)     (не видно)      (видно плохо)              (видно)
```
 
Главный бизнес-вопрос: **какие рекламные активности реально приносят
деньги, и куда направить следующий бюджет.** Целевая метрика — ROMI.
Посчитать её исторически невозможно, так как в данных нет ни одного поля про источник, ни одной
цифры затрат на рекламу.
 
Отсюда две части решения:
1. **Восстановить максимум из прошлого** - что можно вытащить из
   существующих данных о продажах и открытых источников.
2. **Спроектировать measurement-систему на будущее** - чтобы через месяц
   ответ на этот вопрос был получен автоматически.

## Задача 1. Описание данных
 
Источник фактов о продажах — `data/base.xlsx`, выданный
организаторами. Полный разбор с методологией представлены в
[reports/EDA_ВЫВОДЫ.md](reports/EDA_ВЫВОДЫ.md). Здесь — самое важное.
 
| Показатель | Значение |
|---|---|
| Строк в файле | 795 |
| Уникальных покупателей | 606 |
| Курсов | 18 |
| Период | 04.08.2026 — 10.09.2026 (10 сентября обрезан, исключён из анализа) |
| Общая выручка | 5 904 672 ₽ |
| Средний / медианный чек заказа | ~7450 ₽ |
 
**Границу заказа не пришлось подбирать вручную.** Из 189 пар соседних
покупок одного человека 167 совпадают до секунды, а дальше сразу идёт разрыв
минимум в 26 минут.

**Пакетные покупки - основная механика.** 24,4% заказов
содержат больше одного курса, у каждой частой суммы пакета цена делится
на курсы поровну. Самый частый пакет —
14 950 ₽ (56 заказов, 14,2% всей выручки). Пакет поднимает средний чек в 1,66 раза — это кросс-сейл, а не
скидка, и в расчётах он размечен отдельно.
 
**Выходные дают почти половину продаж:** 48% заказов и 45% выручки
приходятся на субботу и воскресенье.
 
**Что в данных отсутствует:** источник трафика, затраты на рекламу,
история до 4 августа. Это и есть причина, почему весь MVP строится как
tracking-система на будущее, а не как доработка исторического анализа.

# Задача 2. Восстановление маркетинговой истории
 
Единого журнала продающих постов, скидок и рекламных размещений у бизнеса
нет. Полный собранный датасет — в
[`research/Восстановление_маркетинговой_истории.xlsx`](research/Восстановление_маркетинговой_истории.xlsx)
 
---

**Цель.** Восстановить максимум маркетинговой активности за
период 05.08–10.09.2026, используя только легально доступные публичные
источники — без доступа к внутренней аналитике канала.


**Источники.**
 
| ID | Источник |
|---|---|
| S1 | Архив канала [t.me/s/postypashki_old](https://t.me/s/postypashki_old) |
| S2, S3 | Telemetr — статистика по каналу |
| S4 | TGStat — открытая аналитика |
| S5 | Архив сайта проекта |
| S6 | YouTube-канал |
| S7 | Пользовательский график продаж (сверка с транзакциями) |
 
**Уровни уверенности** - каждой найденной активности присвоен один из
трёх уровней, а не единая оценка «нашли/не нашли»:
 
- **Очень высокая** - есть конкретный коммерческий триггер/дедлайн, и он
  по времени совпадает с пиком в транзакциях.
- **Высокая** - есть коммерческая активность и близкая по времени
  активность в продажах, но совпадение не такое точное.
- **Средняя** - активность потенциально влияет, но точного пика в данных
  не видно.

 
## Хронология: что нашли и с чем это совпало
 
### До распродажи 9 августа — длинная воронка прогрева
 
Ещё до начала наблюдаемого периода (с января 2026 и особенно с июня) шла
серия активностей: бесплатные вебинары про карьеру в
аналитике/бэкенде, бесплатный курс «Python для алгоритмов», контент вокруг
стажировок Яндекса и Т-Банка, интенсив по ИИ-безопасности. Ни одна из них
не даёт всплеска сама по себе - они формируют накопленный спрос, который
выстрелил 9 августа.
 
### 08–09 августа - финальная распродажа СТАРТ
**Уверенность: очень высокая.**
 
Оффер: любой курс за 6 490 ₽, комбо «Алгоритмы + любой курс» — за 9 990 ₽, только 8–9 августа.
 
**Проверили по транзакциям, а не только по совпадению дат:**
- 50% всех продаж линейки СТАРТ пришлись на это окно — против 4% продаж
  линейки ПРО в это же время;
- 88% пакетов внутри окна содержат курс «Алгоритмы» — против 31% пакетов
  вне окна.


### 20–23 августа — запуск линейки ПРО
**Уверенность: высокая.**
 
Новый продукт (Analytics/ML/Backend/Algorithms/AI Agents PRO), бонус за
запись до 23.08.
 
**Подтверждение:** продажи ПРО выросли с 0,8 до 10,5 заказов в день —
**рост в 13 раз** к моменту дедлайна.
 
### 31 августа – 06 сентября - кампания вокруг стажировки Т-Банка + финальная скидка ПРО
**Уверенность: очень высокая** (обе активности).
 
Внешний дедлайн отбора Т-Банка использован как инфоповод, параллельно шла
скидка на ПРО: 14 795 → 8 950 ₽, только до 06.09.
 
**Подтверждение:** 49 и 45 заказов 4–5 сентября, 8 950 ₽ — доминирующая
цена именно в эти дни.
 
### 07–10 сентября — бесплатная неделя «Аналитика вне SQL»
**Уверенность: средняя.**
 
Лид-магнит с кейсами и разбором вакансий. Скорее формирует новую
воронку, прямой связи с транзакциями не видно.

# Задача 3. Marketing data model

Нужна модель, где по каждому событию видно: кто → что сделал → когда →
откуда пришёл → к какой рекламной активности относится.

Полное описание каждой таблицы и каждого поля — в
[`DATABASE_README.md`](bd/DATABASE_README.md). Здесь — только то, что
специфично именно для этой задачи: как пример из условия лёг на схему,
и одно ключевое решение.

## Сущности из условия → реальные таблицы

| Из условия | В схеме | Если отличается — почему |
|---|---|---|
| `user` | `users` | — |
| `channel` | `placements.channel_name` | канал — атрибут размещения, не отдельная таблица |
| `campaign`, `placement`, `creative` | `campaigns`, `placements`, `creatives` | без изменений |
| `post` | `channel_posts` | — |
| `click`, `bot_start` | `touches.event_type` | оба — одно и то же по смыслу событие ("касание"), разведены только значением enum, не таблицами — иначе каждая модель атрибуции превращается в `UNION` вместо одного запроса |
| `lead` | `interest_events` | расширено до шкалы интереса, а не бинарного "стал лидом / нет" |
| `conversation_started` | `conversations` | без изменений |
| `payment`, `order` | `payments` | заказ — не отдельная таблица, а группировка по правилу из задачи 1 (`student_id` + `ts`), посчитанная в [`src/canonical.py`](../src/canonical.py); хранить её отдельно значило бы держать производные данные, которые могут разъехаться с первоисточником |
| `course` | `courses` | без изменений |

## Единственное решение, которое стоит выделить отдельно

`payments` **не** ссылается на конкретный `touch`. Пользователь может
прийти по нескольким касаниям — таблица `touches` хранит их все, а какое
из них считать причиной покупки, решает модель атрибуции (задача 6), а
не структура БД.

# Задача 4. User stitching

Нужно связать рекламный контакт, Telegram-пользователя, лид и оплату —
без персональных данных, с учётом ограничений Telegram.

## Как передаётся метка размещения

Deep link `t.me/бот?start=<метка>` — стандартный механизм Telegram, до
64 символов. Пользователь кликает по размеченной ссылке → бот получает
код в `/start` → пишет `touch` с этим кодом. Никакого отдельного
протокола придумывать не нужно — задействован штатный инструмент
платформы.

## Если детерминированная связка невозможна

`payments.stitch_method` фиксирует явно, как получена связь:

| Метод | Когда применяется |
|---|---|
| `deterministic` | хэш от `user_id` совпал напрямую |
| `probabilistic` | совпадение по времени и курсу, без прямого совпадения хэша |
| `none` | связать не удалось — поле `hashed_user_id` остаётся пустым |

# Задача 5. Tracking внешней рекламы, своего канала и менеджера

## Два сценария передачи метки — в зависимости от того, куда ведёт реклама


- **Реклама → бот.** Deep link `?start=код` — код разворачивается в
  `campaign_id/placement_id/creative_id` прямо на `/start`.
- **Реклама → сразу в канал**.
  Именной **invite-ссылкой** Telegram (`createChatInviteLink`): если бот =
  админ канала, по `chat_member`/`chat_join_request` видно, сколько
  вступило именно по этой ссылке - без параметра `start`.
Оба варианта пишут в одну и ту же таблицу `touches`, разным значением
`event_type` (`bot_start` / `channel_join`).
 
## Свой канал: как классифицируются публикации
 
Регекс-правила по ключевым словам (`скидка`, `%`, `старт`, `открыт
набор`) размечают `channel_posts.post_type` (`sale_post / discount /
launch / native / content`). LLM-классификатор здесь не даёт
преимущества — простое правило прозрачнее и не ломается на 5-10 постах
в день.
