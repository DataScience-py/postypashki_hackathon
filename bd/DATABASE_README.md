# База данных tracking-бота — описание структуры

Measurement system: сбор хэшированной статистики со всех
каналов (внешняя реклама, собственный канал, менеджер), чтобы понимать,
откуда пришёл пользователь, и уметь считать ROMI по каждому конкретному
Telegram-каналу.

Файлы схемы:
- `schema.dbml` — структура для визуализации ER-диаграммы с типами данных и ограничениями на
  [dbdiagram.io](https://dbdiagram.io).

---

## 1. Ключевые архитектурные решения

### 1.1. Хэшируется `telegram_user_id`, а не `username`

- `username` в Telegram можно менять неограниченное число раз и даже удалить
  полностью — тогда `@username` пропадает совсем.
- `telegram_user_id` (числовой) присваивается один раз при создании аккаунта
  и не меняется никогда.
- Если бы хэшировался нестабильный username, повторные покупки одного и того
  же человека после смены username невозможно было бы связать друг с другом 

**Формула хэширования:**
```
hashed_user_id = SHA-256(app_salt || telegram_user_id)
```
`app_salt` хранится **только** в секрет-хранилище приложения, никогда не в БД и не в репозитории.

### 1.2. Единый журнал `touches`, а не таблица на каждый канал

Все касания пользователя — из внешних рекламных каналов, из своего канала,
из бота, из инвайт-ссылок пишутся в **одну таблицу**, а не в отдельные
таблицы по каждому Telegram-каналу.

**Причины:**
1. Путь пользователя единый: если размещения в 20 разных каналах лежат в
   20 разных таблицах, для attribution/stitching пришлось бы делать UNION по
   всем ним, чтобы восстановить последовательность касаний одного человека.
2. Число каналов не фиксировано и растёт: таблица-на-канал требует менять
   схему БД при каждой новой закупке рекламы — плохо масштабируется и плохо
   для воспроизводимого MVP.
3. Канал — это **атрибут события** (`channel_name`), а не структурная граница
   таблицы. Дифференциация каналов делается фильтрацией по колонкам, а не
   физическим разделением данных.

**Что физически разделяется — источники/коллекторы, а не таблицы назначения:**

| Источник | Что делает | Куда пишет |
|---|---|---|
| Redirect-бот (`/start` deep link) | Логирует клик по внешней рекламе | `touches` (`event_type = bot_start`) |
| Telegram Bot API webhook (`chat_member` / `chat_join_request`) | Логирует вступление по именованной invite-ссылке | `touches` (`event_type = channel_join`) |
| User-клиент коллектор на **сторонних** каналах (Telethon/Pyrogram) | Читает публичную историю купленных размещений | `channel_posts` — метаданные поста, НЕ user-level (коллектор не видит, кто кликнул) |
| User-клиент коллектор на **своём** канале | Читает публичную историю постов | `channel_posts` |

Итог: разделение в схеме идёт по **типу сущности** (что сделал юзер / что
опубликовано / что куплено), а не по тому, из какого Telegram-канала пришли
данные.

## 2. Структура таблиц

### 2.1. `courses` - справочник курсов
Справочник продуктов из `base.xlsx`. `course_name` уникален.

### 2.2. `users` - пользователи
Центральная сущность: `hashed_user_id` — единственный идентификатор человека
во всей системе.

| Поле | Комментарий |
|---|---|
| `first_seen_ts` / `last_seen_ts` | Границы активности — нужны для attribution window и для выявления "холодных" лидов (реактивация). |
| `first_touch_id` | Денормализация: сразу известно первое касание без пересчёта `MIN(ts)`. Циклическая FK-зависимость с `touches` — в `schema.sql` решена отложенным `ALTER TABLE` после создания обеих таблиц. |
| `birth_date` | NULL по умолчанию, заполняется только при явном opt-in-ответе пользователя боту (нужен consent-текст в самом боте). Используется для birthday-кампании. |
| `newsletter_subscribed` / `newsletter_subscribed_ts` | Явный флаг согласия на рассылку — не выводится автоматически из факта переписки. `CHECK` гарантирует, что timestamp проставлен тогда и только тогда, когда флаг = true. |

### 2.3. Иерархия кампаний: `campaigns → placements → creatives → tracking_codes`

- **`campaigns`** — бизнес-инициатива с целью и периодом. `campaign_type`
  различает не только внешнюю рекламу, но и маркетинговые механики: `birthday`,
  `re_engagement`, `recovery`, `referral`, `own_channel` — единая модель для
  платной рекламы и внутренних активностей.
- **`placements`** — конкретное размещение: канал + формат + время + `cost`.
  Именно здесь `cost` и `publication_time`, без которых не считается ROMI.
- **`creatives`** — вариант текста/картинки внутри размещения (для A/B).
- **`tracking_codes`** — короткий код (`a7k2m9`), который реально уходит в
  `?start=` или зашивается в QR. Ограничен `CHECK`-паттерном
  `[A-Za-z0-9_-]{1,64}` — это жёсткое ограничение самого Telegram на длину и
  алфавит deep-link параметра, а не произвольный выбор.

### 2.4. `touches` — журнал касаний

| Поле | Комментарий |
|---|---|
| `tracking_code` | NULL, если это органика (пользователь написал боту без ссылки/кода) — органику тоже логируем, просто без привязки к кампании. |
| `channel_name` | Денормализовано из `placements` для быстрых запросов без лишнего JOIN, даже когда `tracking_code` отсутствует. |
| `event_type` | `bot_start` (deep link) и `channel_join` (invite-ссылка) логируются разными механизмами Telegram API — поэтому это разные значения enum, а не одно "клик". |
| `is_first_touch` | Частичный уникальный индекс `idx_touches_one_first_touch_per_user` гарантирует на уровне БД не более одного `TRUE` на пользователя — это не логика приложения, а constraint. |

### 2.5. `interest_events` — заинтересованность в конкретном курсе

Отдельно от `touches`, потому что touch = "пользователь где-то появился",
а interest = "проявил интерес к конкретному продукту" — разные по силе
сигналы для разных целей: touch — для attribution, interest — для рассылки
и для менеджера.

`interest_level` — градация силы интереса (`clicked_details` →
`asked_price` → `clicked_manager_button`), полезна и для того, кому что
предлагать в рассылке, и для оценки качества лидов по каналам.

**Связь с рассылкой:** при появлении записи в `interest_events` бот может
автоматически предложить подписку на рассылку (если пользователь не отказался
явно) и добавить его в сегмент "интересовался курсом X" — тогда позже можно
таргетированно напоминать именно про этот курс.

### 2.6. `conversations` — прокси на разговор с менеджером

Переписки менеджеров недоступны по условиям кейса — таблица фиксирует не
содержание диалога, а факт и метаданные вокруг него: момент клика по кнопке
"написать менеджеру" (`started_ts`), опциональная связь с `interest_events`
(к какому курсу вёл разговор), тег менеджера для операционной аналитики
загрузки.

### 2.7. `channel_posts` — метаданные публикаций

Пишется user-клиент коллектором (Telethon/Pyrogram) для своего канала и для
сторонних каналов, где куплена реклама. Это метаданные **поста**, а не
событие конкретного пользователя — коллектор физически не видит, кто читал
публикацию. `post_type` классифицируется regex-правилами
(`sale_post / discount / launch / native / content`) и может быть NULL, пока
не классифицирован. `text_excerpt` — короткая выдержка, не полный текст поста.

### 2.8. `operational_calendar` — ручной журнал на будущее

Не про восстановление прошлого, а про то, чтобы перестать терять даты,
скидки и цены с момента запуска системы. Заполняется вручную командой или
через команду бота `/log_event`.

### 2.9. `payments` — стыковка с историческими продажами

| Поле | Комментарий |
|---|---|
| `student_id` | Легаси-идентификатор из `base.xlsx` (хэш от username) — хранится как есть, без изменений. |
| `hashed_user_id` | Новый хэш от `user_id`, заполняется только при успешном stitching. |
| `stitch_method` | `deterministic / probabilistic / none`. `CHECK`-ограничение не позволяет записать `hashed_user_id`, если `stitch_method = 'none'` — это защищает от случайного "притягивания" несвязанных записей. |
| `order_group_id` | Для пакетных покупок — несколько строк `base.xlsx` могут относиться к одному заказу. |

## 3. От продажи к конкретному каналу: как это работает

Схема отвечает на вопрос "из какого именно стороннего Telegram-канала
пришла продажа" — но не напрямую через одно поле, а через цепочку:

```
payments.hashed_user_id
    → touches (все касания этого пользователя)
        → touches.channel_name          ← конкретный канал (не абстрактная "внешняя реклама")
        → touches.tracking_code → tracking_codes.placement_id → placements
            → placements.campaign_id, placements.cost, placements.publication_time
```

**Важный нюанс:** у `payments` нет прямой ссылки на конкретный `touch`.
Это осознанное решение, а не недостаток:

- Если у пользователя было **одно** касание перед покупкой — связь
  однозначна, достаточно `JOIN` по `hashed_user_id`.
- Если было **несколько** касаний (реклама в канале А → свой канал → пост
  со скидкой) — выбор, какому каналу приписать продажу, это уже задача
  **attribution model** (first touch / last touch / linear и т.д.), а не
  задача структуры БД. Схема намеренно хранит **все** касания, чтобы любая
  attribution-модель могла быть применена поверх одних и тех же сырых
  данных, а не поверх заранее выбранного "правильного" канала.

**Пример: last-touch attribution**
```sql
SELECT p.payment_id, p.amount, p.ts AS payment_ts, t.channel_name, t.ts AS touch_ts
FROM payments p
JOIN LATERAL (
    SELECT channel_name, ts
    FROM touches
    WHERE hashed_user_id = p.hashed_user_id
      AND ts <= p.ts
    ORDER BY ts DESC
    LIMIT 1
) t ON true
WHERE p.stitch_method <> 'none';
```

**Пример: ROMI по каналам (first-touch attribution)**
```sql
SELECT t.channel_name, SUM(p.amount) AS attributed_revenue
FROM payments p
JOIN touches t ON t.hashed_user_id = p.hashed_user_id AND t.is_first_touch = TRUE
WHERE p.stitch_method <> 'none'
GROUP BY t.channel_name;
```
Результат сопоставляется с `placements.cost` по каждому каналу для расчёта
ROMI на уровне конкретного стороннего Telegram-канала.

## 4. Ограничения — что система принципиально не может

- **Продажи из `base.xlsx` (795 строк, до запуска бота) не могут быть
  привязаны к конкретному каналу.** На момент этих покупок не было ни
  `touches`, ни tracking-кодов — связать их с каналом невозможно в принципе,
  а не потому что чего-то не хватает в схеме. Это явный пример "что пока
  узнать нельзя" из требований кейса.
- **Deterministic stitching зависит от расхождения хэш-функций** (см. п.1.1)
  — без промежуточной таблицы соответствия username↔user_id historical
  stitching останется вероятностным.
- **`channel_posts` не знает, кто читал пост** — только публичные метрики
  (просмотры, репосты). User-level связь появляется только через
  `tracking_codes`/`touches`, если под постом стояла размеченная ссылка.
